# MossCode 单 Agent 与四 Agent 性能对比

## 1. 实验目的

验证多 Agent 编排是否真的提高工程结果，而不是只增加“角色数量”。本实验采用控制变量：两种模式使用同一个 DeepSeek 模型、相同初始文件、相同任务、相同工具实现、相同命令权限与相同完成门槛；唯一变量是 `single` 或 `multi` 执行模式。

## 2. 基准任务

修复一个带缺陷的 Python 库存模块，要求：库存累加和输入校验、多 SKU 原子预订、失败不产生部分扣减、拒绝重复订单、排序且不可变的快照。固定测试文件包含 6 项 `unittest` 验收，Agent 不得修改测试。每次运行都从完全相同的初始目录开始，Agent 结束后由基准脚本再次独立执行测试。

复现命令：

```powershell
conda run -n web3d-backend python scripts/benchmark_agent_modes.py --repeats 3
```

原始 JSON 保存在 Git 忽略的 `data/benchmarks/<时间>/results.json`，不会包含 API Key。

## 3. 真实结果

测试时间：2026-09-01；模型：`deepseek-v4-flash`；每种模式 3 次。

| 指标 | 单 Agent | 四 Agent |
| --- | ---: | ---: |
| 独立验收成功率 | 3/3（100%） | 3/3（100%） |
| 测试文件保持不变 | 3/3 | 3/3 |
| 平均耗时 | 13.14 秒 | 51.46 秒 |
| 耗时范围 | 11.66-14.30 秒 | 41.49-58.54 秒 |
| 平均模型请求 | 5.00 | 14.67 |
| 平均工具调用 | 6.00 | 16.33 |
| 平均 Token | 13,150 | 36,983 |

四 Agent 在本任务中约为单 Agent 耗时的 3.92 倍、Token 的 2.81 倍。两者均正确修改且通过 6/6 测试，因此本任务没有观察到多 Agent 的成功率收益。

## 4. 如何解释结果

单 Agent 更适合边界清晰、验收明确、影响文件较少的修改。它减少角色交接和重复读取，在相同质量门下速度和成本明显更好。

四 Agent 的额外开销来自 Planner 定义验收、Explorer 独立调查、Coder 实施、Reviewer 再次读取和运行验证。首轮样本中单 Agent 运行一次测试并以结构化证据完成；四 Agent 由 Reviewer 再运行一次测试并明确通过。这个机制在需求含糊、跨模块、高风险改动中更有价值，但不应该无条件用于简单任务。

因此 MossCode 提供三种模式：

- `single`：默认推荐给明确的小中型任务。
- `multi`：推荐给跨模块、需求存在解释空间或需要独立验收的任务。
- `adaptive`：依据任务长度和复杂度信号自动选择，并把实际模式写入事件，方便复盘。

## 5. 实验局限与后续评测

本次样本量较小，且只有一个固定 Python 任务，能够证明性能开销和基本正确性，不能证明所有复杂任务上的总体胜率。后续应扩展为多任务集：跨文件前端功能、后端迁移、只读诊断、安全修复和含模糊需求的任务；重复运行并统计成功率、回归缺陷、人工审查评分和费用。为了公平，不应用模型自述作为成功标准，必须保留独立测试或人工验收。
