# MossCode 面试答辩问答与要求核对

本文用于项目视频录制、现场介绍和评委问答。回答不需要逐字背诵，建议先讲设计目标，再讲取舍和可验证证据。

## 一句话定位

MossCode 是一个不依赖 Agent 框架、能够在用户授权的本机工作区内自主读写文件和执行命令的多智能体编程系统。它把规划、探索、实现、审查分给四个受权限约束的角色，并自行实现上下文、工具循环、完成判定、安全边界和错误恢复。

## 30 秒开场怎么讲

**问：请简单介绍你的项目。**

答：我实现的是一个本地 AgentCode 系统 MossCode。用户给出工作区和任务后，Planner 整理明确要求，Explorer 只读调查代码，Coder 在受限工具集内修改和验证，Reviewer 向主编排器提交证据化复核意见；主编排器持续修复并统一决定最终状态。系统没有使用 LangChain、OpenAI Agents SDK 等 Agent 框架；模型输出解析、工具调用、本地执行、上下文压缩、终止条件、错误恢复和权限审批都是我自己实现的。前端主要解决可观察、可控制和可恢复的问题，用户可以审阅 Diff、批准命令、取消任务或恢复检查点。

## 核心设计问答

### 1. 为什么设计成四个 Agent，而不是一个 Agent？

答：单 Agent 同时负责理解、搜索、修改和验收，容易在已有假设上自我确认。我的拆分依据不是为了堆数量，而是为了分离职责和权限：Planner 不碰文件，Explorer 只读，Coder 才能写入，Reviewer 不能写入。这使错误更容易定位，也让最危险的能力只暴露给确实需要它的角色。四个角色串行还让证据链非常清晰，适合本地编程任务和答辩展示。

### 2. 这是真正的多 Agent，还是同一个提示词换了四个名字？

答：它们共享底层模型客户端，但拥有独立系统提示、工具白名单、消息窗口、轮次上限和目标。Agent 在这里指具备独立角色状态、决策上下文和行动权限的执行单元，不要求必须使用四个不同模型。关键区别是角色边界会被后端代码强制执行，而不是只靠提示词自觉。

### 3. 为什么采用串行协作，没有让四个 Agent 并行？

答：当前目标是稳定完成单个本地任务。Planner 的计划是 Explorer 的输入，Explorer 的证据又是 Coder 的输入，Reviewer 必须看到最终改动，所以天然存在依赖。串行能避免多个写入者争用同一文件，也便于复现。未来适合并行的是多个只读 Explorer 或 Git worktree 隔离的候选方案，而不是让多个 Coder 直接修改同一个目录。

### 4. 为什么 Planner 不使用工具？

答：Planner 的职责是从用户需求中提炼目标、约束和验收条件，不应该过早陷入某个文件实现。实际项目事实由只读 Explorer 提供。这样既减少无意义工具调用，也能检查计划是否在看到代码后仍成立。

### 5. 为什么 Reviewer 没有写文件权限？

答：如果 Reviewer 一边审查一边偷偷修复，它就很难保持独立判断，最终结果也无法区分“实现通过”还是“审查阶段又改过”。Reviewer 只能读取和必要时验证；发现问题时必须标明它来自明确用户要求、失败验证还是本轮回归，并给出证据和一个最小动作。它没有最终裁决权，主编排器判断意见是否合法后再交给 Coder 修正。

### 6. 多 Agent 会不会只是增加 Token 和延迟？

答：会，而且我做了真实 A/B 测试，不回避这个代价。同一 DeepSeek 模型、同一库存修复任务各运行 3 次，两种模式都是 3/3 通过；单 Agent 平均 13.14 秒、13,150 tokens，四 Agent 平均 51.46 秒、36,983 tokens。四 Agent 多做独立探索和 Reviewer 复验，但在边界清晰的任务上没有成功率收益。因此系统现在提供单 Agent、四 Agent 和自适应路由：简单任务优先单 Agent，跨模块、含糊或高风险任务才用四角色。多 Agent 是风险控制手段，不是默认越多越好。

## 自研核心逻辑问答

### 7. 你如何证明没有套用现成 Agent 框架？

答：可以直接从依赖和调用链证明。后端依赖是 FastAPI、Uvicorn、HTTPX、python-dotenv 等通用库，没有 Agent SDK。`orchestrator.py` 自己维护角色循环，`roles.py` 定义角色权限，`registry.py` 定义并执行本地工具，`context.py` 组织历史上下文，`sqlite_store.py` 持久化状态。模型服务只返回文本或 tool call，不替我执行代码和文件操作。

### 8. 一次 Agent 循环具体怎么运行？

答：后端先构建当前角色可见的上下文和工具 schema，然后请求模型。如果模型返回 tool call，系统验证工具是否存在、角色是否有权调用、参数是否符合要求，再在本地执行，将结构化结果作为 tool message 放回上下文。模型可以继续调用工具或给出角色结论。每次循环前都会检查取消、轮次上限和重复调用，角色结束后再进入下一个角色。

### 9. 你怎么解析模型输出？

答：优先解析模型原生的 `tool_calls`，读取函数名和 JSON 参数；对于兼容服务的差异格式做归一化。解析后不会直接执行，而是经过 schema 校验、工具白名单、路径安全和命令策略。JSON 无法解析、字段缺失或工具不存在时，会形成可反馈给模型的结构化错误，而不是让整个进程崩溃。

### 10. 怎么避免 Agent 无限循环？

答：有多层终止条件：角色有最大轮次，检查型角色有预算，同一工具和相同参数的重复调用达到阈值后会阻止继续；明确的角色最终文本会结束当前角色；用户取消会在模型、工具和角色边界终止流程。整个任务最后还必须满足任务类型对应的完成证据。

### 11. 为什么之前会出现“其实完成了但系统判失败”？后来怎么解决？

答：早期设计把 Reviewer 当成终审者，而且每轮都让它重新解释整份长需求，因此它既可能漏掉 `PASS`，也可能不断新增 `if __main__` 之类用户没有要求的规范。现在验收范围冻结为用户原始任务；拒绝必须包含 `BASIS/EVIDENCE/ACTION`，返工复审只检查上一项问题和同一测试产生的回归。最后写入后已有成功验证时，无依据的范围扩张不会触发失败；真正的测试失败仍会由主编排器继续交给 Coder 修复。

### 12. 如果任务要求修改文件，但 Coder 什么都没写，会怎样？

答：系统会根据任务意图判断是否需要写入。需要修改的任务必须出现成功写入证据，否则即使模型口头说“完成”也会以 `required_change_not_written` 失败。只读检查任务则允许零写入完成，避免把“没有改文件”统一误判为失败。

### 13. 命令第一次失败、后来成功，为什么最终还能完成？

答：验证不是“一次失败永久失败”，而是按时序判断。只要失败原因被修复，最后一次相关验证成功，且其后没有新的失败，就可以成为完成证据。UI 会把早期失败折叠为“已恢复”，既保留审计记录，也不会用过期错误误导用户。

## 上下文和持久化问答

### 14. 对话历史怎么管理？为什么不能把全部历史都发给模型？

答：全部历史会让 Token 成本不断增长，也会把旧工具输出和过时信息带入当前决策。我把历史分成三层：较早轮次压缩为持久摘要，保留最近三轮原始对话，再加入当前任务；进入单个角色后还会裁掉过旧的工具消息。这样在固定预算内保留长期目标和最近细节。

### 15. 你做的是真正的长期记忆吗？

答：它是面向项目对话的持久记忆，而不是无限容量的通用人格记忆。会话、轮次和摘要保存在 SQLite 中，后端重启后仍能恢复。旧轮次被压缩，所以它保留事实和决策，不保证逐字复现全部历史。这个边界是有意设计的，可以控制成本和上下文污染。

### 16. 为什么选择 SQLite？

答：这是单机本地工具，SQLite 无需部署数据库服务，事务、索引和迁移能力足以支撑会话、事件、Execution 和检查点元数据。它比只放内存可靠，也比一堆 JSON 文件更适合并发状态更新。若未来做云端多用户版，再换 PostgreSQL 更合理。

### 17. 用户在 Agent 思考时继续输入，如何处理？

答：前端不会锁死输入框。补充消息先作为新 Turn 写入数据库，并以 FIFO 排队；当前工具调用不会被粗暴插断，而是在一轮安全边界结束后衔接下一条消息。这样既满足“见缝插针”的交互感，也避免在文件写到一半时改变任务语义。

## 工具与安全问答

### 18. Agent 为什么能够操作本机终端？

答：不是模型直接获得终端，而是模型提出结构化工具请求，后端决定是否执行。`run_command` 在用户选择的工作区内启动子进程，捕获输出、退出码和超时，并把结果返回模型。模型永远拿不到一个无限制的远程 Shell。

### 19. 怎么防止 Agent 修改工作区以外的文件？

答：所有文件路径都先规范化和解析，再验证最终绝对路径是否位于工作区根目录内；`..`、绝对越界路径和符号链接逃逸都会被拒绝。命令执行同样固定工作目录，并额外做高风险模式拦截。提示词中的“不要越界”只是辅助，真正边界由后端代码保证。

### 20. 为什么还要提供“自动、询问、禁止”三种命令模式？

答：不同用户和任务的风险容忍度不同。自动模式适合本地开发效率，普通验证命令可直接运行；询问模式适合陌生仓库，每条命令都需要单次批准；禁止模式只允许文件工具。无论哪种模式，高风险命令都不会因为批准而绕过硬拦截。

### 21. 如何处理用户和 Agent 同时修改一个文件？

答：GUI 保存文件时必须提交打开文件时的 `expected_sha256`。后端写入前重新计算当前哈希，不一致就返回冲突，要求用户刷新，而不是静默覆盖。检查点恢复也比较 Agent 写入后的哈希，检测到人工后续修改时拒绝强制恢复。

### 22. 为什么检查点不直接依赖 Git？

答：用户工作区可能不是 Git 仓库，也可能本身有未提交改动。每轮文件级检查点独立于 Git，可以精确恢复 Agent 本轮首次修改前的内容，不污染用户提交历史。检查点保存在被忽略的本地目录中，恢复仍需要用户明确确认。

### 23. Hooks 和 MCP 会不会违反“不使用 Agent SDK”的要求？

答：不会。它们是我在核心工具层之上实现的可选扩展协议，不负责替我做编排、上下文或终止判断。Hooks 默认关闭并继续受审批规则约束；MCP 首版只实现本地 stdio 的 `tools/list` 和 `tools/call`，工具仍要经过角色白名单，写入型工具必须审批。核心系统在不配置它们时完全可运行。

## 前后端架构问答

### 24. 为什么任务接口要改成后台 Execution？

答：模型和命令可能运行数分钟，如果 HTTP 请求一直阻塞，刷新页面或网络闪断就会丢失前端状态。现在创建 Execution 后立即返回 ID，后台状态写入 SQLite，SSE 只负责实时通知。页面刷新后可重新查询状态，取消和重试也有明确对象。

### 25. 为什么使用 SSE，而不是 WebSocket？

答：当前实时数据主要是后端单向推送进度和结果，用户指令、审批、取消仍可用普通 HTTP。SSE 实现更简单，浏览器原生支持自动重连，也更适合事件日志模型。若以后加入真正的双向流式终端，再考虑 WebSocket。

### 26. GUI 对 Agent 本身有什么价值，不只是美化吗？

答：GUI 承担的是控制面和证据面：选择工作区、设置权限、批准命令、继续输入、取消与重试；同时展示 Markdown 结果、文件树、Diff、终端输出和检查点。内部四角色过程被压缩为自然进度，避免 JSON 噪声，但详细记录仍可折叠查看。这比单纯给命令行套壳多了安全交互和恢复能力。

### 27. 为什么默认只让用户看到统一结果？

答：内部角色文本常包含重复计划、工具参数和机器化 JSON，直接展示会淹没真正有用的信息。用户需要的是“现在做到哪里、最终改了什么、验证是否通过”。因此公开层只显示阶段性自然语言和最终总结，底层事件仍用于 Diff、终端和审计。

## 反思与追问

### 28. 当前设计最大的不足是什么？

答：第一，四角色固定串行，对非常简单任务有额外延迟；第二，长记忆摘要目前是规则化压缩，复杂项目中可能损失少量细节；第三，本地命令安全采用白名单与风险模式，不等同于操作系统级沙箱；第四，MCP 还不支持远程 OAuth。答辩时主动说明边界比把系统描述成“完全安全、完全自主”更可信。

### 29. 如果继续迭代，你最先做什么？

答：当前已经有确定性的自适应路由，并用真实 A/B 基准记录耗时、模型请求、工具调用和 Token。下一步我会把固定信号路由升级为由多任务基准集校准的策略，再用 Git worktree 隔离并行候选方案，最后在 GUI 增加成功率、费用和人工接管面板。优先顺序仍是先提升可测量的任务质量，再扩展并行度。

### 30. 如何评价这个 Agent 做得好不好？

答：不能只看最终回复是否流畅。我看任务成功率、独立测试通过率、测试是否被篡改、未经要求的文件改动、工具失败恢复、模型请求、Token 和耗时。仓库已有可复现的单/多 Agent 基准脚本，Agent 结束后由脚本独立运行测试；当前固定任务中两种模式均 3/3 成功，但四 Agent 耗时约 3.92 倍。这个结果用于校准自适应路由，后续还要扩展为跨前端、迁移、诊断和安全修复的多任务集。

### 31. 这个项目中你最想让评委看到的设计是什么？

答：我最想展示的是“可证明的完成”而不是“模型说完成”。文件写入、命令结果和 Reviewer 结论都是结构化事件；需要修改的任务必须有写入，最后写入后必须有有效验证，明确拒绝意见不能被覆盖。这个设计来自实际调试中遇到的假成功和假失败，也最能体现我理解 Agent 不只是 Prompt，而是一个受状态、证据和权限约束的软件系统。

## 2 分钟视频建议脚本

### 0:00 - 0:15 项目定位

展示主界面并说：这是我独立实现的本地多智能体编程系统 MossCode，不使用任何 Agent 框架。四个角色分别负责规划、探索、实现和审查，核心工具循环与安全控制都由后端实现。

### 0:15 - 1:15 完成一个真实任务

选择一个专用演示工作区，输入一个能在一分钟内完成且可验证的任务，例如：

> 为当前静态网页增加一个可切换的深色模式，偏好写入 localStorage，并运行现有测试或新增最小验证。

画面重点拍到：任务发送、自然语言阶段进度、用时、文件发生变化、命令验证通过。不要打开 `.env`，也不要展示包含 Key 的终端环境变量。

### 1:15 - 1:45 展示可审查与可恢复

## 面试表达原则

- 先讲“为什么这样设计”，再讲用了什么技术。
- 不要说“绝对安全”或“完全自主”，应明确工作区边界、风险命令拦截和当前局限。
- 不要把四角色数量当亮点，重点是职责、权限与证据隔离。
- 被问到 AI 辅助开发时可以如实回答，并强调自己能解释每项设计、测试和取舍。
- 回答实现问题时主动指出对应文件，让评委知道结论可以在代码中验证。
- 若现场结果异常，优先展示持久事件、Diff 和终端证据，说明系统为什么作出该状态判断。
